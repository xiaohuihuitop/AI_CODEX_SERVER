# App Server 实时同步协议优化

## 目标

在保留官方 Codex Desktop 的前提下，将跨端控制与同步稳定在 Desktop 内置 `codex.exe app-server` 上，使手机/Web 发出的消息可幂等到达、运行过程自动更新、完成状态及时收敛，并确保官方桌面发起的对话仍能被可靠观察。

## 已确认事实

- 正式控制面已经固定为 Desktop 内置 App Server；CDP、DOM 自动化和重启 Codex 均不是可接受方案。
- Agent 启动的 App Server 与官方 Desktop 内部 App Server 是两个进程，不能把前者的运行内存状态当成后者的状态。
- Desktop 侧栏可见线程以本地 SQLite 目录为准，归档线程不得由 App Server `thread/list` 重新带回。
- 当前客户端缺少 `initialized` 通知，并会把携带 `id` 的 App Server 主动请求误判为响应后丢弃。
- 当前普通同步每轮只处理一个线程；线程数量较多时，Desktop 来源的新内容可能需要较长时间才被轮询到。
- JSONL 是最终持久化记录，但不应继续承担 Agent 自己发起回合的唯一实时通知职责。

## 功能需求

### R1 JSON-RPC 协议完整性

- `initialize` 成功后必须发送 `initialized` 通知。
- 必须区分响应、通知和 App Server 主动请求；主动请求禁止静默丢弃。
- 客户端关闭、子进程退出和协议错误必须使所有未完成请求明确失败。
- App Server 版本兼容性必须由当前 Desktop 内置运行时生成的 Schema 或等价契约测试约束。

### R2 幂等发送与控制

- 每次手机/Web 用户消息必须生成稳定且唯一的 `clientUserMessageId`，并随 `turn/start` 发送。
- 同一控制请求因断线、重试或重复投递时不得创建多个回合。
- 停止操作必须关联明确的 `threadId` 与 `turnId`，并能区分已完成、已停止和失败。

### R3 Agent 来源回合实时同步

- Agent 自己发起的回合以 App Server 通知作为实时主链路。
- 事件至少覆盖回合开始、内容增量、工具/处理过程、完成、失败和线程状态变化。
- 手机/Web 无需手动刷新即可收到新内容和状态变化。
- JSONL 写入后进行最终对账；不一致必须记录并修正，不能静默覆盖。

### R4 Desktop 来源回合兼容同步

- 官方 Desktop 发起的回合继续以 SQLite 可见线程目录和 JSONL 变更作为观察链路。
- 文件或目录变化应优先调度对应线程，避免在大量线程中等待完整轮询周期。
- 归档线程必须从 relay、手机/Web 列表和本地缓存中物理移除。

### R5 有序事件与断线重对账

- 跨 Agent、relay、手机/Web 的事件必须携带单调序号、唯一事件 ID、线程 ID、回合 ID、来源和观察时间。
- relay 和客户端必须按事件 ID 去重；检测到序号空洞或重新连接时，必须触发目标线程快照对账。
- 对账是显式协议行为，不得通过猜测状态或长期显示“进行中”来兜底。

### R6 分层状态与可诊断日志

- 界面状态必须分开表达：云端连接、Agent 在线、App Server 就绪、线程状态、回合状态。
- 状态必须有更新时间和过期规则；过期后显示未知/待确认，禁止无限累计等待时间。
- 日志必须包含请求 ID、线程 ID、回合 ID、事件序号、重试/去重/对账原因，并继续限制最多 500 条。

### R7 历史加载一致性

- 默认加载最新 5 轮，向上加载时使用稳定的 `turnId` 游标，每次增加 5 轮。
- 分页合并必须保持新旧消息顺序，禁止加载更早历史后覆盖或丢失最新内容。

## 非范围

- 不替换、修改或打补丁官方 Codex Desktop。
- 不恢复 CDP、调试端口、DOM 自动化或自动重启 Codex。
- 不保证 Agent 发起的回合立即出现在另一个 App Server 进程控制的 Desktop 当前页面；该限制必须在产品状态中如实表达。
- 不增加文件上传、远程文件浏览或无关的管理功能。
- 不进行手机 App 正式打包；开发验证使用 Web 和 HBuilderX 调试安装。

## 验收标准

- [x] 初始化链路严格执行 `initialize -> initialized`，主动请求不再被误判或静默丢弃。
- [x] 相同 `clientUserMessageId` 的重复控制请求最多产生一个回合，服务端和 Agent 均有去重证据。
- [x] `codex_temp` 同一线程连续从 Web 发送 3 条消息，3 条均到达且顺序一致，电脑端回复自动显示在 Web，无需手动刷新。
- [x] Agent 来源回合开始、增量、完成/失败状态通过实时事件自动更新；JSONL 最终对账后内容一致。
- [x] Desktop 来源回合在本地记录变化后 5 秒内触发目标线程同步，不依赖扫描完全部线程。
- [x] 断开并恢复 Agent/relay 连接后，事件空洞能被检测，目标线程自动对账且无重复消息。
- [x] 已归档线程不会重新出现在手机/Web 列表；历史向上分页不会覆盖最新 5 轮。
- [x] 运行状态不会永久停留在“进行中”；状态过期、协议错误和不支持的主动请求均可从日志定位。
- [x] `server` 与 `desktop` 的测试、静态检查全部通过，并新增真实 App Server 契约/集成测试。
- [x] 全流程验证期间不关闭、不重启、不注入官方 Codex Desktop 进程。

## 风险与约束

- App Server 协议会随 Desktop 内置版本变化，Schema 检查失败时应阻止发布并明确报错，禁止自动切换控制方案。
- Windows 文件监听可能出现合并或丢事件，因此监听只负责加速调度，周期性目录/JSONL 校验负责发现遗漏；这是同一数据源的对账机制，不是替代数据源的 fallback。
- App Server 主动审批和用户输入请求需要明确的远程交互协议；首轮至少保证不会静默挂起，完整 UI 按实现阶段验收。
